# Настройка превью мердж-реквестов с помощью GitLab Review Apps

GitLab Review Apps создают для каждого мердж-реквеста отдельную временную копию сайта документации.
Ревьюеры читают собранный сайт вместе с изменениями в исходном тексте.
В руководстве показано, как опубликовать превью прямо из артефактов заданий CI без собственного веб-сервера, связать их с мердж-реквестом и настроить их автоматическую очистку.
Все, что описано в руководстве, работает на любом тарифе GitLab.

Руководство — для инженеров по документации, у которых сайт на Antora уже собирается в GitLab CI.

В примерах используется репозиторий документации вымышленного продукта Red Apple Conference, созданного по образцу реальной платформы.
Группа `red-apple` публикует сайт на GitLab Pages, а GitLab открывает превью на том же домене Pages.

## Что понадобится

- Репозиторий документации на Antora, который уже собирается в GitLab CI.
- Если в `.gitlab-ci.yml` есть `workflow:rules`, они должны разрешать пайплайны мердж-реквестов (`merge_request_event`).
- Включенный на сервере GitLab Pages: GitLab отображает превью на домене Pages.
  На GitLab.com Pages включен.
  Если у вас собственный сервер GitLab, уточните это у администраторов.
- Для приватного или внутреннего проекта — контроль доступа GitLab Pages, включенный на сервере, чтобы GitLab проверял, кому разрешено открывать превью.
  На собственном сервере GitLab его включает администратор.

## Опубликуйте превью для каждого мердж-реквеста

Превью — это обычная сборка Antora, которую задание сохраняет как артефакты.
Артефакты — файлы, которые GitLab хранит после завершения задания.
Эти файлы отдает сам GitLab, поэтому отдельный шаг публикации в пайплайне не нужен.
Добавьте задание `deploy-review`:

```yaml
deploy-review:
  stage: deploy
  image: node:22
  variables:
    PREVIEW_URL: "https://red-apple.gitlab.io/-/docs/-/jobs/$CI_JOB_ID/artifacts/build/site"
  script:
    - npm ci
    - npx antora antora-playbook.yml --url "$PREVIEW_URL"
  artifacts:
    paths:
      - build/site
    expire_in: 7 days
  rules:
    - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'
```

Ключевое слово `rules` разрешает запуск задания только в пайплайнах мердж-реквестов, поэтому опубликованный сайт оно не затрагивает.
Задание собирает сайт в стандартную выходную директорию Antora, `build/site`, и сохраняет эту директорию как артефакты.

GitLab отображает HTML из артефактов как веб-страницы только на домене Pages.
Поэтому `PREVIEW_URL` указывает на домен Pages, а не на адрес самого GitLab.

`PREVIEW_URL` собирает адрес превью из четырех частей:

- `red-apple.gitlab.io` — домен Pages группы.
  На собственном сервере GitLab замените `gitlab.io` на домен Pages этого сервера.
- `/-/docs` — проект, отделенный префиксом `/-/`.
- `/-/jobs/$CI_JOB_ID/artifacts` — артефакты текущего запуска задания.
  GitLab подставляет вместо `$CI_JOB_ID` числовой идентификатор задания, поэтому каждый пуш публикует новое превью по новому адресу.
- `/build/site` — путь внутри артефактов, то есть выходная директория Antora.

Флаг `--url "$PREVIEW_URL"` переопределяет продакшн-URL из плейбука: URL сайта Antora становится адресом превью.
Antora записывает URL сайта в собранные страницы.
Заметнее всего он в ссылке на главную страницу — в названии сайта в верхней панели.
С переопределением эта ссылка ведет внутрь превью, а не на продакшн-сайт.

:::note
На тарифах GitLab Premium и Ultimate каждое превью можно разместить по отдельному пути на домене сайта — для этого есть параллельные развертывания GitLab Pages.
Превью из артефактов, описанные в этом руководстве, решают ту же задачу на любом тарифе GitLab.
:::

## Свяжите превью с мердж-реквестом

Задание уже публикует превью, но у ревьюера пока нет ссылки на него.
Добавьте блок `environment`, чтобы ссылка на превью появилась в мердж-реквесте:

```yaml
deploy-review:
  # ...
  environment:
    name: review/$CI_MERGE_REQUEST_IID
    url: $PREVIEW_URL/index.html
```

`environment.name` создает отдельное окружение для каждого мердж-реквеста.
На странице **Environments** эти окружения собраны в группу `review`.

`$CI_MERGE_REQUEST_IID` — номер мердж-реквеста, который виден в его URL и заголовке.

`environment.url` — адрес, который GitLab добавляет в мердж-реквест.

Адрес заканчивается на `index.html`, потому что браузер артефактов отдает только файлы: ссылка на директорию `build/site` возвращает ошибку 404.

GitLab добавляет на страницу мердж-реквеста кнопку **View app**.
Каждый пуш запускает новое задание, и у превью появляется новый адрес.
Кнопка всегда открывает последнюю сборку.

Когда пайплайн завершится, нажмите **View app**, чтобы открыть превью в браузере.

:::note
После добавления `deploy-review` пуш в ветку мердж-реквеста может запускать два пайплайна: пайплайн ветки с вашими прежними заданиями и пайплайн мердж-реквеста с `deploy-review`.
GitLab берет статус мердж-реквеста из пайплайна мердж-реквеста.
Проверки, которые работают только в пайплайне ветки, например сборка или линтер, на этот статус больше не влияют.

Чтобы проверки остались в статусе мердж-реквеста, запускайте их и в пайплайнах мердж-реквестов.
Подробнее — в разделе [Configure merge request pipelines](https://docs.gitlab.com/ci/pipelines/merge_request_pipelines/#configure-merge-request-pipelines) документации GitLab.
:::

## Настройте автоматическую очистку превью

Превью нужно, только пока мердж-реквест открыт.
Отдельное задание для очистки не нужно: достаточно двух настроек и встроенного поведения GitLab.
Полная конфигурация:

```yaml
deploy-review:
  stage: deploy
  image: node:22
  variables:
    PREVIEW_URL: "https://red-apple.gitlab.io/-/docs/-/jobs/$CI_JOB_ID/artifacts/build/site"
  script:
    - npm ci
    - npx antora antora-playbook.yml --url "$PREVIEW_URL"
  artifacts:
    paths:
      - build/site
    expire_in: 7 days
  rules:
    - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'
  environment:
    name: review/$CI_MERGE_REQUEST_IID
    url: $PREVIEW_URL/index.html
    auto_stop_in: 7 days
```

`artifacts:expire_in` удаляет сохраненную сборку через неделю после завершения задания.
Исключение — последняя успешная сборка каждой ветки: GitLab хранит ее и после этого срока.
Поэтому открытый мердж-реквест не теряет актуальное превью, а устаревшие сборки удаляются.

Окружение тоже останавливается автоматически.
GitLab останавливает его после слияния или закрытия мердж-реквеста, поэтому отдельное задание для остановки не нужно.
Настройка `auto_stop_in: 7 days` останавливает окружение, если в течение недели не было новых пушей.

Чтобы увидеть активные превью, откройте страницу **Environments** проекта и найдите группу `review`.

## Устранение неполадок

Если превью не работает, причина обычно в правилах задания, путях к артефактам или URL сайта.

### Кнопка View app не появляется

Задание `deploy-review` не запустилось для мердж-реквеста.

Откройте пайплайн мердж-реквеста и проверьте, есть ли в нем это задание.
Если задания нет, убедитесь, что его `rules` срабатывают на `merge_request_event`, а `workflow:rules`, если они есть, разрешают пайплайны мердж-реквестов.

### Браузер показывает исходный HTML или скачивает файл

Адрес превью указывает на сам GitLab, а не на домен Pages, или домен Pages недоступен.

GitLab отображает HTML из артефактов как веб-страницы только на домене Pages, поэтому сначала проверьте домен в `PREVIEW_URL`.
Если домен указан правильно, уточните у администраторов, включен ли GitLab Pages на сервере.
Для приватного или внутреннего проекта также уточните у администраторов, включен ли на сервере контроль доступа GitLab Pages.

### URL превью возвращает ошибку 404

Путь в URL не совпадает с тем, куда задание сохранило сайт, или срок хранения превью истек.

Сравните путь после `artifacts` в `PREVIEW_URL` со значением `artifacts:paths` задания: в обоих должна быть одна и та же директория — `build/site`.
URL также должен заканчиваться именем файла: ссылка на директорию возвращает ошибку 404.
Если адрес верный, проверьте, когда завершилось задание: сохраненные сборки удаляются по истечении срока `expire_in`.

### Название сайта ведет на продакшн-сайт

Название сайта в верхней панели — это ссылка на главную страницу.
Если в превью она открывает продакшн-сайт, значит, сайт собран без флага `--url`.
Antora строит эту ссылку из URL сайта, а в плейбуке указан продакшн-URL.
Проверьте, что задание собирает сайт с `--url "$PREVIEW_URL"`.
Перенаправление на стартовую страницу и остальные ссылки относительные, поэтому работают и без флага.
